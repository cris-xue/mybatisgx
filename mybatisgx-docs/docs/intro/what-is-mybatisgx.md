# 什么是 MyBatisGX

> 防腐是根，优雅是枝

## 概述

MyBatisGX 是一个基于 MyBatis 的增强型 ORM 框架。它不是 MyBatis-Plus 的替代品，也不是 JPA 的模仿者，而是为「追求持久层防腐与编码优雅」的开发者准备的。

框架的一切能力——方法名查询、QueryEntity、MGXQL、MGXSQL、关联查询——都是从「防腐」这个根上生长出来的枝丫。

## 防腐：根

「防腐」是 MyBatisGX 存在的根本原因，指的是**防止持久层逻辑腐蚀业务层与架构**。

在企业级项目长期演进中，最常见的腐蚀模式有两种：

### 查询逻辑的失序（业务层的腐蚀）

Wrapper、Specification、Criteria 可以在任何地方拼装查询条件，查询语义随之散落在各 Service 方法中。随着时间推移：

- 同一张表的相似查询在多个 Service 里被反复拼装
- 数据库字段名侵入业务代码
- 改动一个字段，无法评估影响范围
- 查询逻辑从集中走向分散，从清晰走向混乱，从可控走向失控

这就是持久层的「熵增」。MyBatisGX 通过 **DAO 层收敛**——所有查询以方法定义、QueryEntity、MGXSQL 等形式显式定义在 DAO 层——从机制上阻止查询逻辑向业务层泄漏。

### 黑盒运行时的不可控（架构的腐蚀）

JPA 类框架通过持久化上下文、脏检查、隐式 Flush 等方式接管运行时行为。这些机制带来开发效率的同时，也让 SQL 变得不可见、不可预测、不可干预。性能问题难以定位，数据库特性无法使用，架构的演进被黑盒绑架。

MyBatisGX 的选择是：**不引入任何黑盒机制**。所有 SQL 生成与执行时机都是显式、可预测、可覆盖的。

## 优雅：枝

「防腐」决定了不做什么，「优雅」决定了怎么做。

MyBatisGX 吸收其他框架的精华——如复用 JPA 成熟的注解语义进行对象建模——**前提始终是保证防腐与优雅**：

- 复用 JPA 注解做「结构描述」，但不引入 JPA 的运行时机制
- 借鉴方法名查询的高效，但约束它必须在 DAO 层定义
- 拥抱 XML 的可控性，让它成为复杂查询与性能优化的归属

所有能力都是根上长出的枝丫：方法名查询、QueryEntity、MGXQL、MGXSQL、自动关联查询、批量操作……它们服务同一个目的——让持久层代码保持清晰、可控、可演进。

```
                  ┌────────────────────────────┐
                  │          防腐（根）          │
                  │  防止持久层逻辑腐蚀业务与架构 │
                  └────────────────────────────┘
                     │      │      │       │
          ┌──────────┼──────┼──────┼───────┼──────────┐
          ▼          ▼      ▼      ▼       ▼          ▼
       方法名查询   QueryEntity  MGXQL   MGXSQL  关联查询  批量操作
        （都是根上长出的枝丫，一切能力都服务于防腐与优雅）
```

## MyBatisGX 与 JPA 的关系

**MyBatisGX 并不是 JPA 的替代品，也不是 MyBatis 与 JPA 的折中产物。**

我们复用 JPA 中成熟、被长期验证的元数据表达方式（如实体映射与关联注解），只是为了统一对象模型与关系描述的语义——**这是在「保证防腐与优雅」前提下吸收他框架精华的范例**。

在 MyBatisGX 中：

- 不会引入 EntityManager、Session 生命周期
- 不存在持久化上下文（Persistence Context）
- 不会发生隐式 SQL 执行、脏检查或自动 Flush
- 任何 SQL 的生成与执行时机都是显式、可预测、可覆盖的

**JPA 注解在 MyBatisGX 中只承担「结构描述」的角色，而不参与「行为控制」。**

所有 SQL 仍然遵循 MyBatis 的执行模型：
- SQL 可被预生成
- SQL 可被 mapper.xml 完全接管
- SQL 的最终形态始终对开发者可见、可干预

## 核心理念

```
MyBatisGX = 防腐 + 优雅
```

如果你厌倦了 JPA 的黑盒运行时，也厌倦了 Wrapper 拼装带来的持久层失序，那么 MyBatisGX 正是为这种矛盾需求而生。

## 支持的数据库

支持 10+ 种主流数据库，包括 MySQL、Oracle、PostgreSQL、MariaDB、达梦（Dameng）、人大金仓（Kingbase）、GaussDB、OceanBase 等，详见 [核心特性](./features)。

## 适用场景

- 希望减少样板代码，但不想牺牲 SQL 可控性
- 希望查询逻辑收敛在 DAO 层，不侵入 Service 层
- 希望使用声明式关联查询，但不想引入 JPA 的复杂性
- 希望持久层长期保持清晰、可控、可演进（防腐）
- 希望在 AI 时代减少上下文负担，让代码更加简洁
